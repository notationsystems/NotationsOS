# Production path

`/production` is one continuous path from a source observation to a versioned information product, in seven stages: source → acquisition → normalization → candidate build → inspection → notation → release. It is the frontend of the milestone stated on 2026-09-06: one complete path from a real observation to an inspectable, versioned product. It operates the existing local production rail ([Local acquisition-to-candidate workflow](LOCAL_PRODUCTION_WORKFLOW.md)) from the browser, with the rail's own receipts, and it states, at each stage the path cannot yet continue, exactly which contract or authority is missing and who owns it. Present tense throughout: what the code does today.

## What it is

Everything the path is as data lives in `src/domain/productionPath.ts`: the seven stages, a closed state vocabulary, the derivation of each stage's state from what the rails actually produced, the request-identity rule, the recovery vocabulary, and the blockers. The screen (`src/components/production/ProductionPath.tsx`, served by `src/app/production/page.tsx`) renders that derivation and sends the closed commands of `payload.production-command.v1`. It holds no copy of the corpus, computes no digest, decides no admission, resolves no identity and activates no release.

The path has two modes, decided by the rail, not by the page. With `npm run dev:production` (or `PAYLOAD_PRODUCTION_LOCAL=1` on a loopback origin), the rail answers its catalog and the page is `LOCAL RAIL`: every receipt on it is a real local artifact. Anywhere else the rail answers its disabled descriptor and the page is `FIXTURE`: the committed demonstration (`src/fixtures/production/demo.json`, produced through the same rails from the committed examples at fixed instants) stands on the path as `DEMONSTRATION`, the console is replaced by the enable command, and nothing pretends to run.

## The stages and their states

| Stage | What it does | State today, live rail |
|---|---|---|
| Source | An observation is taken from a declared source under an operator policy | `READY` for the committed synthetic Carrier bytes or pasted bytes; `DONE` where the operator's real FMCSA capture is read back, with the adapter blocker |
| Acquisition | The bytes enter the evidence rail unchanged, with a content digest and a receipt, under an INGEST decision | `WAITING` until the corpus and source are registered, then `READY`, then `DONE`, `FAILED` or a historical retry |
| Normalization | A fixed adapter parses the bytes under a contract, under a separate DERIVE decision | `READY` once an acquisition exists; `DONE` with a candidate or `QUARANTINED` with the bytes and the reasons retained |
| Candidate build | Explicit members are assembled under a knowledge cutoff into an UNADMITTED build | `READY` once a NORMALIZED run exists; a quarantine is never a member |
| Inspection | Every object is reopened by exact reference; integrity is recomputed; nothing is repaired | `READY` once any run has an output |
| Notation | An operator's interpretation refers to exact evidence | `BLOCKED`: the kernel's command set has no attach command |
| Release | Admitted information is published as a versioned release | `BLOCKED`: no admission authority exists; every build stays UNADMITTED |

The state vocabulary is closed: `READY`, `DONE`, `RUNNING`, `FAILED`, `QUARANTINED`, `WAITING`, `BLOCKED`, `DEMONSTRATION`. Each has one meaning, shown on hover. A stage that is `DONE` carries the exact `{kind, id, digest}` of its object and the run that produced it. A stage that is `BLOCKED` carries its blocker: what is missing, which contract owns it, and what would change it.

## Identities, receipts and recovery

One run name yields five request identities (`<name>-corpus`, `-source`, `-capture`, `-normalize`, `-build`) under the rail's identifier rule, applied in the browser so a refused name never reaches the rail. An identity, once used, names its inputs forever: the identical command returns the historical receipt (`EXISTING`, `historicalRetry: true`, the original times, no new execution); a changed command under the same identity is `REQUEST_CONFLICT`; an intentional new attempt is a new identity. "Use a new request identity" on a step renames that step and every later one (`-a2`, `-a3`, …), because their inputs change with it; the failed request keeps its identity and its receipt.

Every receipt is rendered as the rail returned it: `run.state`, then `run.stages` stage by stage with state, code and outputs, so `NOT_RUN` stays `NOT_RUN` (a capture leaves extraction unperformed) and a quarantine shows extraction `QUARANTINED` and normalization `NOT_RUN`. A confirmed failure shows its code, whether the artifact, the receipt and the run receipt were retained (`UNCONFIRMED` stays `UNCONFIRMED`), its remediation codes with their meaning, and the recovery the rail's own retry policy permits. A transport refusal (`payload.production-error.v1`) shows its code, the backend's message, its details, and the recovery its code permits.

Recovery is a closed vocabulary derived from the rail's, never invented: retry the identical request (discovers the historical outcome; re-executes nothing), use a new request identity, inspect the retained outputs, inspect the quarantine, correct the input, wait and retry, enable the rail, choose an eligible member, operator review. Every remediation code and every transport refusal the rail emits is covered (`src/domain/productionPath.test.ts` asserts the list); an unknown code is shown verbatim with review as its only recovery. Nothing on the page deletes history, repairs a record, removes a lock or reruns an incomplete operation.

Inspection sends exactly `{id, digest}` (the rail refuses anything else) and renders the answer with its flags first: `integrity RECOMPUTED_LOCAL`, `historical true`, `currentPermissionGranted false`, `rawBytesIncluded false`, `canonicalAdmission false`. An acquisition shows its evidence, receipt, source policy, capture time and INGEST decision; a normalization its DERIVE decision, reasons and candidate (fields, missing fields as missing, `UNRESOLVED` identity with `canonicalId: null`, valid time, knowledge time, provenance with the acquisition one click away); a build its members with their candidate, identity state, source class, knowledge time and DERIVE-at-build decision; a run its stages; unbound content its byte count with no acquisition, binding or receipt claimed. The full answer is always available as returned.

## The real source

The one real observation the system holds is the FMCSA Company Census capture of USDOT 80806, taken by the operator CLI on 2026-09-05 under a time-bounded internal qualification policy ([Local source connectors](LOCAL_SOURCE_CONNECTORS.md)). The path's source card shows the checked-in request, the policy declaration (its window, purposes, operations, audiences and retention, from the same code the capture is evaluated against), the fifteen pinned fields, and the readback.

The readback is `GET /api/production/source-captures/<requestId>`, under the same flag and loopback guard as the rail. It constructs the source-capture store over the operator's qualification root (`PAYLOAD_SOURCE_QUALIFICATION_DIR`, default `.payload/source-qualification`; a request never selects a root) and calls its read-only inspection, which recomputes local integrity and reads neither the network nor the clock. It answers the inspection with its non-claims (`collectionPerformed false`, `providerContacted false`, `rawBytesIncluded false`, `canonicalAdmission false`, `customerDistributionPermitted false`), or `SOURCE_CAPTURE_NOT_FOUND` where the capture is not in that root, or the store's own integrity refusal. An absent root is read as not found and nothing is created there. The acceptance runner points this at an isolated empty root, so acceptance never reads operator data.

Where the capture is found, the source stage is `DONE` and shows the state, capture time, byte count, digests, the returned records with `identityStatus UNRESOLVED` and `canonicalId null`, and `notReturned` as not returned.

The observation continues by operator command, not on the HTTP rail ([Real-source continuity](REAL_SOURCE_CONTINUITY.md)): `npm run source -- normalize` applies the source-specific adapter `fmcsa.company-census-observation/v1` to the retained capture and produces a typed, `UNADMITTED` `FMCSACompanyCensusObservation` candidate; `npm run source -- build` assembles exact normalization references into a `payload.local-candidate-build.v2` build. Two more guarded routes read those back the same way, through the stores' own inspections: `GET /api/production/source-normalizations/<normalizationId>` and `GET /api/production/source-builds/<buildId>`, answering `CENSUS_NORMALIZATION_NOT_FOUND` or `CENSUS_BUILD_NOT_FOUND` where the record is not on this machine, and with `derivationPerformed false`, `assemblyPerformed false`, `providerContacted false` and the rest of the non-claims where it is. The source card shows the normalization's state, its declared backend time, its DERIVE decision, the candidate with its identity (`UNRESOLVED`, `canonicalId null`), its separate clocks (capture time, provider last-modified, filing date as a source filing date and not a valid time, valid time not established by the snapshot), and every one of the fifteen fields with presence (`PRESENT`, `EXPLICIT_NULL`, `OMITTED`), raw text, typed value, unit and interpretation; and the build with its definition, knowledge cutoff, exact members and membership root. The identifiers are the checked-in requests' (`examples/sources/fmcsa-company-census-normalize.json`, `-build.json`), which pin the operator's actual history and cannot be recreated in a fresh clone.

The source stage's blocker names the boundary that remains: neither operation is on the HTTP rail, whose NORMALIZE still takes only `caravan.carrier-json/v1` and `payload.ifc-artifact/v1`, so the path reads the real observation's continuation and cannot run it; and no admission contract takes the build further.

## Beyond the rail

**Notation.** Once a build exists, the card shows the reference a notation would carry for it, in the frontend's `payload.notation-evidence-reference.v0` (kind `CANDIDATE_BUILD`, the exact target and digest, the build context and time, an empty interpretation), copyable, marked `attachment DISABLED`. The kernel's closed command set has no `ATTACH_EVIDENCE_REFERENCE`; the contract request is recorded in [Notation workspace](NOTATION_WORKSPACE.md). References are not encoded into notation text.

**Release.** What exists is the committed corpus: releases with certification, production record and supersession under `/releases`, answered as-of through `/stream`. What does not exist is a route from a candidate build into one of them: no versioned profile evaluates a build and records admission, refusal or unresolved requirements, so nothing can enter a release and every build stays `UNADMITTED`. The owner is the admission contract ([Cross-repository baseline](CROSS_REPOSITORY_BASELINE.md): one authoritative route for evaluation, identity, version history and release eligibility); the remedy is a reviewed, committed contract and then an internal release separate from demonstration fixtures.

## What the design does not bend

- The rail decides. Every state on the path is derived from a receipt the rail returned or a contract that exists; the page infers no completion, no admission and no identity.
- HTTP 200 is not completion. The run's own state and stages are what is shown.
- An identity names its inputs forever. The page never reassigns one, never backdates, never reruns an incomplete operation.
- Nothing withheld, nothing raw. Inspection carries no bytes and no paths; the readback carries no bytes and no paths; the page shows what the rail answers.
- Blockers are named, not implied. A stage that cannot continue says what is missing, who owns it and what would change it.
- Acceptance never reads operator data. The runner isolates both the evidence root and the qualification root.
